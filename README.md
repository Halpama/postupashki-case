# Оценка эффективности рекламы в Telegram: атрибуция и ROMI для онлайн-школы «Поступашки»

> Бизнес видит только факт оплаты и не знает, какая реклама привела покупателя.
> Мы восстановили маркетинговую историю канала, спроектировали измеримую систему
> (учёт → атрибуция → экономика) и реализовали MVP, который считает ROMI честно:
> с маржой, окнами, уровнями достоверности и инкрементальностью.
>
> **628** заказов-кандидатов · **606** покупателей · **5 904 672 ₽** выручки за 38 дней ·
> **24 из 74** постов канала в архиве · **100%** исторических продаж без источника.

---

## Проблема

Из пяти шагов воронки (реклама → просмотр → основной канал → менеджер → оплата) бизнес
измеряет **один последний**. Маркетинговые касания исторически не логировались:
в выгрузке 795 продаж нет ни источника, ни расходов, ни просмотров.

**Следствие:** ROMI не считается ни по внутренней, ни по внешней рекламе; бюджет распределить
нельзя; органику от неорганики отделить нельзя. Аудит выгрузки (`audit_sales.py`) даёт
`unknown_source_share = 1.0` — то есть **исторический ROMI невосстановим в принципе**.
Всё, что можно посчитать по прошлому, помечено `confidence='estimated'` и не выдаётся за факт.

## Решение: три слоя

| Слой | Что делает |
|---|---|
| **1. Учёт** | реестр размещений (`channel → campaign → placement`), event-контракт из 11 типов событий + 3 запрещённых, склейка по каноническому ключу `user_id = hash(tg_id)` |
| **2. Атрибуция** | 6 моделей распределения выручки, окна по типу активности (обоснованы лаг-анализом), `unknown ≠ organic`, повторная покупка = новый эпизод, возвраты уменьшают доли исходных касаний |
| **3. Экономика** | атрибуционный ROMI от маржи + инкрементальный ROMI (ITT, ДИ по Ньюкомбу), порог окупаемости, план на бюджет 300 000 ₽ |

**Два ROMI, два вопроса.** Атрибуционный — «кому записать продажу» (распределение наблюдаемой
выручки, от маржи). Инкрементальный — «создали ли мы продажу» (прирост относительно контрфакта,
анализ ITT). Решения о масштабе принимаются по инкрементальному; метрики не складываются.

## Ключевые результаты

- **Продажи идут волнами запусков, а не органикой:** лаг-анализ по истории канала —
  день поста +56% к базовой выручке дня, +1 день +25%, +2 дня +8% → эффект затухает за 2–3 дня,
  это и есть обоснование атрибуционного окна 3–7 дней.
- **Пакеты подтверждены данными:** все 145 двухкурсовых заказов дают круглые розничные цены
  (14 950 ₽ ×56, 9 900 ₽ ×24, 13 950 ₽ ×15, **9 990 ₽ ×14 — буквально пример из условия кейса**),
  поэтому `amount` = доля пакета, а `SUM(amount)` = цена чека: выручка 5 904 672 ₽ корректна.
- **Продающие посты удалены — и именно на них пики:** в архиве 24 поста из 74 идентификаторов (32%);
  пики 09.08 (524 092 ₽), 05.09 (484 684 ₽) и 04.09 (269 585 ₽) приходятся на окна удалённых
  `msg_id` 1835 и 1879. Маркетинговая история восстановлена как гибрид «сохранившиеся посты +
  карта дырок + следы в уцелевших текстах» с `confidence='estimated'`.
- **Инкрементальность измерима в рамках бюджета:** для lift +1,5 п.п. при p₀=5% нужно
  3 780 участников на группу (7 560 всего), а охват одного посева — 9–35K просмотров.
  Тест 20 каналов ≈ 100 000 ₽ — треть бюджета 300 000 ₽.
- **Порог окупаемости:** при марже инфопродукта 80% размещение окупается начиная с ROMI 25%
  (по выручке); при марже 70% — с 43%. Пример из задачи 5 в пересчёте на маржу: 757% → 500%,
  186% → 100%, 90% → 33%.

## Быстрый старт

Python 3.10+, **только стандартная библиотека** — установка пакетов и сеть не нужны.

```bash
# 1. Демо: 6 моделей атрибуции × 4 окна на полностью синтетических данных
python3 mvp/romi_calculator/demo.py

# 2. Воспроизводимый аудит предоставленной выгрузки продаж
python3 mvp/romi_calculator/audit_sales.py data/base.csv --output outputs/real_sales_audit.json

# 3. Атрибуция на произвольном входе (orders + touches, JSON)
python3 mvp/romi_calculator/attribution.py examples/synthetic_journeys.json \
        --model last_non_direct --window-days 7 --output outputs/attribution_result.json

# 4. Тесты
python3 -m unittest discover -s mvp/romi_calculator/tests -v
```

Выходы: `outputs/real_sales_audit.json` (аудит реальных данных),
`outputs/synthetic_model_comparison.csv` и `outputs/synthetic_allocations.csv`
(сравнение моделей, `data_origin='synthetic'`), `outputs/synthetic_experiment.json`
(учебный RCT: 65/1000 против 50/1000 → +1,5 п.п., 95% ДИ [−0,55; +3,57] п.п.).

## Что MVP делает и чего не утверждает

**Делает:** распределяет чистую выручку заказа по подтверждённым касаниям шестью моделями
в четырёх окнах; сворачивает повторные клики; сбрасывает эпизод при повторной покупке;
учитывает возвраты (включая отрицательные суммы); распределяет деньги в копейках
(сумма долей по заказу = 1); маркирует неполную историю (`partial` / `unknown`);
считает ITT-разницу конверсий с интервалом Ньюкомба и планировочный размер выборки.

**Не утверждает:** не восстанавливает неизвестные исторические источники; не подключается
к Telegram; не проводит реальный эксперимент; аудит сумм не подтверждает фактическую денежную
выручку без сверки с платёжным шлюзом; калькулятор инкрементальности не проверяет валидность
дизайна. Атрибуция не равна причинности — это сказано в каждом отчёте.
